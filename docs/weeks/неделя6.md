# Неделя 6 — прескоринг на Airflow

Пакетный скоринг отложенной выборки по команде оркестратора и бизнес-отчёт, который пишет компактная языковая модель по уже посчитанным числам. Краткий обзор — в [README](../../README.md#неделя-6--прескоринг-на-airflow).

## Что изменилось по сравнению с неделей 5

| | Было (недели 3–5) | Стало (неделя 6) |
|---|---|---|
| Режим работы | только онлайн: операция оценивается в момент запроса | плюс прескоринг: вся выборка за период оценивается по команде |
| Кто запускает | человек в интерфейсе оператора | оркестратор Airflow, DAG `prescoring` |
| Контейнеров | 5 | 7 (+ `airflow`, + `ollama`) |
| Таблиц в базе | 3 | 9 (+ `holdout_transactions`, `scored_transactions`, `prescoring_runs`, `business_reports`, `llm_attempts`) |
| Что видит руководство | панель с метриками модели | текстовое резюме в деньгах: предотвращено, потеряно, чистый эффект |

Онлайн-контур (`backend`, `frontend`, `dashboard`) не менялся: добавлен только маршрут `GET /reports/latest` и блок с отчётом внизу панели.

## Запуск

```bash
copy .env.example .env
docker compose up -d --build                         # первая сборка 10–20 минут
docker compose exec ollama ollama pull qwen2.5:3b    # модель для отчёта, однократно, ~2 ГБ
docker compose ps                                    # db, backend, airflow — (healthy)
```

На Windows то же самое делает **`zapusk_docker.bat`**. Веб-интерфейс Airflow — http://localhost:8083, пользователь `admin`, пароль `AIRFLOW_ADMIN_PASSWORD` из `.env`. Запуск DAG: кнопка ▶ на странице DAG или **`zapusk_dag.bat`** (он же печатает отчёт и запись о запуске и сохраняет их в `reports/week6/`).

> Adminer работает на **8081**, Airflow доступен на **8083** (в контейнере Airflow слушает порт 8080).

### Выборка преподавателя

Файл кладётся в `data/holdout.csv` (поля датасета Sparkov + `is_fraud`). Задача `load_holdout` грузит его сама, если таблица пуста. Чтобы заменить выборку на новую:

```sql
TRUNCATE holdout_transactions, scored_transactions, labels CASCADE;
```

Отдельная колонка `transaction_id` не нужна: в таблице она объявлена как `GENERATED ALWAYS AS (trans_num) STORED` — номер операции из датасета и есть уникальный идентификатор.

## DAG prescoring

```
create_tables → load_holdout → extract → score → load → summarize → build_facts → generate_report → check_report
└──────────────────── часть 1: прескоринг ─────────────────────┘   └────────── часть 2: бизнес-отчёт ──────────┘
```

| Задача | Что делает | Почему так |
|---|---|---|
| `create_tables` | выполняет `airflow/dags/sql/tables.sql` (`CREATE TABLE IF NOT EXISTS`) | `db/init.sql` не подходит: он срабатывает только при инициализации **пустого** тома `pgdata` |
| `load_holdout` | `COPY` из `data/holdout.csv`, если таблица пуста | повторный запуск не задваивает выборку; лишние колонки файла (`Unnamed: 0`) отбрасываются |
| `extract` | `COPY (SELECT …) TO STDOUT` во временный CSV | через XCom уходит только путь и параметры запуска |
| `score` | отбрасывает `is_fraud`, вызывает `score_df` из `score.py` для версий v2 и v1 | `@task.external_python` — задача исполняется в окружении модели |
| `load` | одна транзакция: `DELETE` оценок этих версий → `COPY` новых | идемпотентность; `COPY` вместо `insert_rows` — быстрее и без ошибки `numpy.int64` |
| `summarize` | сверяет `count(scored) == count(holdout)`, пишет `prescoring_runs` | расхождение = ошибка, задача падает |
| `build_facts` | SQL-агрегаты → финансовые показатели → готовые строки `facts` | все вычисления здесь, до языковой модели |
| `generate_report` | промпт → Ollama, до 3 попыток, каждая в `llm_attempts` | при числе не из фактов — повтор с подсказкой |
| `check_report` | сверяет числа, пишет `business_reports` | отчёт сохраняется в любом случае, даже непрошедший |

Параметры запуска (`threshold`, `review_cost`, `commission_rate`, `llm_model`, `compare_model`, `llm_attempts`) читаются из **Airflow Variables** со значениями по умолчанию в коде: Admin → Variables, без правки файлов. Подключение к базе — **Airflow Connection** `antifraud_db` из переменной окружения `AIRFLOW_CONN_ANTIFRAUD_DB`.

### Почему два окружения Python

Airflow 2.10 требует `pandas < 2.2`, а модель обучена на `pandas 3.0.6` / `numpy 2.5.3` / `scikit-learn 1.9.1` / `LightGBM 4.7` на Python 3.13. В одном окружении они не уживаются. Решение: в образе `airflow/Dockerfile` рядом с самим Airflow создаётся venv `/opt/airflow/model-venv` на Python 3.13 с версиями из `airflow/requirements-model.txt`, а задача `score` объявлена как `@task.external_python(python=MODEL_PYTHON)` — Airflow запускает её отдельным процессом в этом venv. Так артефакты `.pkl` читаются ровно теми версиями, которыми были записаны.

### Таблицы

| Таблица | Содержимое |
|---|---|
| `holdout_transactions` | выборка: поля датасета, `is_fraud`, `transaction_id` (генерируется из `trans_num`) |
| `scored_transactions` | `PRIMARY KEY (transaction_id, model_version)`, оценка, решение, порог, `run_id`, время |
| `prescoring_runs` | запись на запуск: объём, срабатывания, TP/FN/FP и суммы, финансовые показатели, допущения, `facts`, статус |
| `business_reports` | `run_id`, модель LLM, факты (`JSONB`), текст, `check_passed`, лишние числа, число попыток |
| `llm_attempts` | все попытки генерации: текст, прошла ли проверка, лишние числа, время — для анализа работы LLM |

## Финансовые показатели

Считаются SQL-запросом по `holdout_transactions ⋈ scored_transactions` и формулами в `report_lib.compute_finance`.

| Показатель | Формула | Результат (v2, порог 0,5) |
|---|---|---|
| Предотвращённые потери | сумма `amt` по TP | 113 операций, 71 541 USD |
| Понесённые потери | сумма `amt` по FN | 18 операций, 3 022 USD |
| Ложные блокировки | сумма `amt` по FP | 1 операция, 23,49 USD |
| Операционные затраты | (TP + FP) × `review_cost` | 114 × 2 = 228 USD |
| Упущенный комиссионный доход | сумма FP × `commission_rate` | 0,35 USD |
| **Чистый эффект** | предотвращённые − затраты − упущенный доход | **71 313 USD** |
| **Покрытие мошенничества** | предотвращённые / вся сумма фрода | **96,0%** |

Сравнение версий (дополнительная часть): v1 предотвратила бы 70 663 USD, чистый эффект 70 437 USD — на 876 USD меньше, чем v2.

### Допущения и их обоснование

| Допущение | Значение | Обоснование |
|---|---|---|
| Валюта | USD | датасет Sparkov — операции по картам в США |
| Стоимость ручной проверки | 2 USD | 4–5 минут работы аналитика при ставке ≈ 25–30 USD/час. В неделях 1–2 мы брали 3 у.е., но там в цену входил звонок клиенту; здесь — только просмотр операции |
| Комиссия банка | 1,5% | типичная межбанковская комиссия по картам в США (1,5–2%); банк теряет её, когда блокирует честную покупку |

Меняются в Admin → Variables (`review_cost`, `commission_rate`) и применяются со следующего запуска. **При удвоении обеих ставок** (4 USD и 3%) чистый эффект падает с 71 313 до 71 085 USD, то есть на 228 USD (0,3%): у модели всего 114 срабатываний и одна ложная блокировка, поэтому вывод отчёта не меняется. На модели с тысячами срабатываний эти допущения решали бы всё.

## Отчёт и проверка чисел

Языковая модель **не считает**: она получает готовые строки и должна переписать их символ в символ.

```python
facts = {
  "период": "02.12.2020 – 11.12.2020",
  "операций": "38 981",
  "срабатываний": "114",
  "предотвращённые_потери": "113 операций на сумму 71 541 USD",
  "понесённые_потери": "18 операций на сумму 3 022 USD",
  "покрытие_мошенничества": "96,0%",
  "ложные_блокировки": "1 операция на сумму 23,49 USD",
  "операционные_затраты": "228 USD",
  "упущенный_доход": "0,35 USD",
  "чистый_эффект": "71 313 USD",
  "сравнение_с_прежней_версией": "прежняя версия предотвратила бы потери на сумму 70 663 USD, чистый эффект 70 437 USD",
}
```

### Итоговый промпт

```
Ты финансовый аналитик банка. Подготовь резюме результатов
прескоринга для руководителя подразделения финансового мониторинга.

Требования:
- Используй только значения из блока ФАКТЫ без изменений: копируй числа вместе с подписями.
- Не выполняй вычислений, не округляй, не добавляй новые показатели и проценты.
- Не пиши других чисел: ни номеров пунктов, ни количества предложений, ни дат, которых нет в фактах.
- Не используй терминологию машинного обучения.
- Пиши по-русски, обычным текстом без списков и заголовков.
- Объём 5–7 предложений: общий итог, предотвращённые потери,
  понесённые потери, ложные блокировки и их стоимость,
  одно предложение о сравнении с прежней версией,
  один вопрос для обсуждения с руководством.

ФАКТЫ:
{facts}
```

Генерация идёт с `temperature: 0.2` и `seed: 42` — при тех же фактах ответ воспроизводится. Если проверка не прошла, к промпту добавляется строка с конкретными лишними числами и просьбой переписать; всего до 3 попыток (`llm_attempts`).

### Как устроена проверка

```python
_NUM = re.compile(r"\d{1,3}(?:[  ]\d{3})+(?:[.,]\d+)?|\d+(?:[.,]\d+)?")

def numbers(s):            # «71 541» — одно число; «96,0» и «96.0» — одно и то же
    return {re.sub(r"\s", "", n).replace(",", ".") for n in _NUM.findall(s)}

allowed = set().union(*(numbers(v) for v in facts.values()))
extra = numbers(report) - allowed      # числа, которых нет во входных данных
check_passed = not extra
```

Проверка покрыта тестами: `tests/test_report.py` (6 тестов, запускаются без Airflow и Ollama — `python -m pytest tests/test_report.py`). Они ловят в том числе типичный случай «модель пересчитала»: текст «чистый эффект 71 313 USD, это на 12% больше, а потери 3 000 USD» даёт `extra = {12, 3000}`.

**Что проверка не ловит:** неверный смысл при верных числах. Если модель напишет «понесённые потери 71 541 USD», а «предотвращённые 3 022 USD», оба числа есть в фактах и проверка пройдёт. Поэтому отчёт читает человек, а каждое число в нём можно подтвердить SQL-запросом к базе.

### Анализ работы языковой модели

Скрипт `airflow/tools/llm_eval.py` (`llm_analiz.bat`) берёт факты последнего запуска, генерирует отчёт N раз с разными `seed` и пишет сводку в `data/llm_eval_<модель>.md`: доля прошедших проверку с первой попытки, какие именно лишние числа встречались, среднее время генерации.

Разработка и отладка DAG велись на заглушке Ollama (локальный HTTP-сервер, который отвечает заранее собранным текстом и в каждой третьей первой попытке намеренно добавляет «(рост на 12%)»). На этом стенде проверялось главное: лишнее число ловится, повторная попытка с подсказкой проходит, `check_passed` и `attempts` корректно попадают в базу. **Цифры по реальной qwen2.5 нужно получить запуском `llm_analiz.bat` на машине с Ollama** и вписать сюда.

Ожидаемые проблемы компактных моделей и меры, уже заложенные в код:

| Проблема | Мера |
|---|---|
| Модель пересчитывает проценты и суммы | в промпте явный запрет считать и округлять; проверка чисел |
| Добавляет номера пунктов и маркеры списка | требование писать сплошным текстом без списков |
| Придумывает даты | период передан готовой строкой, запрет на другие даты |
| Случайный разброс между запусками | `temperature: 0.2`, фиксированный `seed` |
| Не исправляется с первого раза | до 3 попыток, в повторный промпт подставляются конкретные лишние числа |

Если доля прошедших проверку низкая: перейти с `qwen2.5:1.5b` на `3b` (Variable `llm_model`), сократить число показателей в `facts` или упростить формулировки промпта.

## Сценарий демонстрации

| # | Что делаем | Что показываем |
|---|---|---|
| 1 | `docker compose up -d` | `docker compose ps`: 7 сервисов, `db`, `backend`, `airflow` — healthy; DAG `prescoring` в интерфейсе |
| 2 | `SELECT count(*) FROM holdout_transactions;` | 38 981 — исходная выборка |
| 3 | ▶ в Airflow | Graph view: все 9 задач зелёные; лог `score` — «колонка is_fraud удалена до скоринга: True» |
| 4 | `SELECT count(*) FROM scored_transactions WHERE model_version='v2';` | 38 981 = объём выборки; в `prescoring_runs` появилась запись |
| 5 | ▶ ещё раз | `count` не изменился — дубликатов нет |
| 6 | `SELECT report_text, check_passed FROM business_reports ORDER BY created_at DESC LIMIT 1;` | текст отчёта и «проверка пройдена»; то же внизу панели :8502 |
| 7 | Admin → Variables → `review_cost` = 4 → ▶ | операционные затраты в отчёте стали 456 USD |
| 8 | `docker compose stop ollama` → ▶ | `generate_report` краснеет после 2 повторов, скоринг и факты уже в базе; `start ollama` → **Clear** на `generate_report` → достаточно двух задач |

Подтверждение числа из отчёта SQL-запросом:

```sql
SELECT count(*) AS tp, round(sum(h.amt)) AS tp_sum
FROM holdout_transactions h JOIN scored_transactions s USING (transaction_id)
WHERE s.model_version = 'v2' AND s.is_fraud_pred = 1 AND h.is_fraud = 1;
-- 113 | 71541  — ровно то, что в строке «предотвращённые потери»
```

## Ограничения

- Отчёт ретроспективный: он опирается на фактические метки `is_fraud`. В эксплуатации метки приходят с задержкой (расследование, чарджбэк — недели), поэтому в день прескоринга такой отчёт собрать нельзя: можно показать только число срабатываний и суммы под подозрением.
- Airflow запущен в режиме `standalone` (планировщик, веб-сервер и база метаданных в одном контейнере, SequentialExecutor). Для учебного стенда этого достаточно, для промышленной нагрузки нужен отдельный executor.
- `score` обрабатывает всю выборку одним куском (≈ 40 с на 39 тыс. операций, пик памяти ≈ 2,1 ГБ). На миллионах строк понадобилось бы разбиение по дням.
- Расписание не включено (`schedule=None`): выборка у нас статическая, запуск ручной.
- Разделение на два DAG через Datasets не делали — процесс короткий и всегда выполняется целиком.
