# Антифрод-пайплайн — общие правила проекта

Ты пишешь код для командного проекта из трёх человек (A, B, C). Здесь описан общий фундамент: данные, разбиение, метрика, интерфейсы. Он одинаковый для всех. У каждого участника есть личное задание в `tasks/TASK_*.md` — там его признаки и модель.

**Главный принцип:** признаки и гипотезы придумывают люди, ты их реализуешь. Не добавляй признаки по своей инициативе. Если видишь хорошую идею, предложи её списком в ответе и жди решения.

Язык комментариев и отчётов — русский. Язык кода (имена переменных, функций) — английский.

---

## 1. Задача

Процессинговый центр банка. На каждую транзакцию нужно выдать вероятность мошенничества, решение (0 — пропустить, 1 — отдать аналитику) и до трёх коротких причин. Заказчика интересуют деньги банка, добросовестные клиенты, которых зря остановили, и понятные объяснения.

Приоритеты оценки (из ТЗ): придуманные признаки и гипотезы → честность проверки → объяснение решений → работоспособность пайплайна → документация → и только потом числа.

## 2. Данные

- Файл: `data/fraudTrain.csv` (Sparkov, ~1,3 млн строк, 01.01.2019 – 21.06.2020, 1000 карт, ~800 мерчантов).
- **`fraudTest.csv` не открывать и не использовать нигде.** На нём нас проверят преподаватели.
- Внешние данные и API запрещены.

Особенности датасета, которые учитывает `src/data.py`:

| Поле | Что делаем |
|---|---|
| первая колонка без имени (`Unnamed: 0`) | удалить, это индекс |
| `trans_date_trans_time` | **единственный источник времени** → колонка `ts` (datetime) |
| `unix_time` | не использовать: в Sparkov сдвинут на годы и не совпадает с датой |
| `merchant` | у всех мерчантов префикс `fraud_`, это не метка. Префикс срезать |
| `cc_num` | идентификатор карты, только для группировки, не признак |
| `trans_num` | идентификатор операции, только ключ |
| `first`, `last`, `street`, `zip`, `job` | персональные данные, в признаки не идут |
| `dob` | → `age` на момент операции (лет, float) |
| `lat/long`, `merch_lat/merch_long` | доступны, но смотри `TASK_A` про гео-гипотезу |
| `is_fraud` | метка; во входе `score.py` её нет |

Типы: `category`, `merchant`, `state`, `gender` → `category`; суммы и координаты → `float32`. Сортировка всегда по `(ts, trans_num)`.

## 3. Разбиение по времени (фиксированное, не менять)

Пусть `T_max` — время последней операции в файле.

| Часть | Период | Для чего |
|---|---|---|
| `train` | всё до `T_max − 122 дня` | обучение модели и популяционных статистик (`fit`) |
| `valid` | следующие 61 день | ранняя остановка, калибровка, выбор порога и политики, сравнение признаков |
| `holdout` | последние 61 день | **финальный честный замер, запускается один раз** командой после выбора финала |

Признаки считаются по **всему** отсортированному потоку, и каждый признак смотрит только в прошлое. Поэтому у первых операций `valid` есть нормальная история из `train`. Разбиение применяется к строкам, а не к истории.

Холдаут открывается только флагом `--holdout` и только для финального конфига. Каждый запуск на холдауте записывается в `reports/experiments.csv` с пометкой.

## 4. Экономика и метрика

Цифры заказчика: проверка аналитиком — 3 у.е.; пропущенный фрод — `amt + 5`; ложная блокировка — 25; ёмкость аналитиков — **не более 0,3% операций за календарный день**.

Трактовка (зафиксирована в `reports/decision_log.md`): операция, отправленная аналитику, на время проверки задерживается.

| Решение \ Факт | фрод | не фрод |
|---|---|---|
| отправили аналитику (1) | 3 | 3 + 25 = 28 |
| пропустили (0) | amt + 5 | 0 |

- `loss_none` = сумма `amt + 5` по всему фроду (системы нет).
- **`savings = loss_none − loss_policy`** — главная метрика («сколько денег экономит пайплайн»).
- Дневной лимит: `k_d = floor(0.003 · n_d)`, где `n_d` — число операций за день в оцениваемых данных. Политика, которая хотя бы в один день его превышает, считается невалидной.

Дополнительные метрики (печатаются всегда): PR-AUC; recall по количеству и **recall по деньгам** (доля суммы фрода, отправленной аналитику); precision среди отправленных; среднее число отправленных в день.

Accuracy и ROC-AUC как главную метрику не использовать: при доле фрода ~0,5% они ничего не говорят о решении заказчика.

Реализация — `src/economics.py`. Базовые политики, которые должны быть всегда:
- `top_p`: каждый день отправлять `k_d` операций с наибольшей вероятностью;
- `rule_amt`: каждый день отправлять `k_d` самых дорогих операций (правило «смотреть всё дороже X» при той же ёмкости);
- `none`: никого не отправлять.

Остальные политики (по ожидаемым потерям и т.п.) делает участник C.

## 6. Интерфейс блока признаков (обязателен для всех)

```python
# src/features/<block>.py
PREFIX = "a_"                        # a_, b_, c_; у base префикса нет
FEATURES: list[str]                  # все колонки, которые блок умеет считать
MONOTONE: dict[str, int] = {}        # необязательно: +1 / -1 для LightGBM
REASONS: dict[str, str]              # шаблон причины для аналитика, по-русски, с {placeholders}

def fit(train_df: pd.DataFrame) -> dict:
    """Популяционные статистики ТОЛЬКО по train. Ничего не знает о valid/holdout."""

def transform(df: pd.DataFrame, state: dict) -> pd.DataFrame:
    """df отсортирован по (ts, trans_num) и может содержать историю.
    Возвращает DataFrame с тем же индексом и колонками FEATURES.
    Значение в строке i зависит только от строк с ts < ts_i (плюс поля самой строки i)
    и от state."""
```

Правила для `transform`:
- Поля самой операции (сумма, категория, время, мерчант) использовать можно: они известны в момент операции. **Её метку нельзя.**
- История карты — только строго более ранние операции. Для скользящих окон `closed="left"`. Операции с одинаковым `ts` друг друга не видят.
- Метки прошлых операций можно использовать только с задержкой (см. `TASK_C`, по умолчанию 30 дней) и только в блоке C.
- Нет истории → разумное значение по построению (сглаживание к популяции) или NaN. Падать нельзя никогда.
- Скорость: весь файл (1,3 млн) за один блок — не дольше ~2 минут на ноутбуке. Циклы по строкам в Python только там, где без рекурсии не обойтись, и тогда по numpy-массивам.

Реестр: `src/features/__init__.py` → `BLOCKS = {"base": base, "a": profile, "b": velocity, "c": context}`.

## 8. Модели (`src/models.py`)

Общий интерфейс: `fit(X, y, X_valid, y_valid, sample_weight=None)`, `predict_proba(X) -> np.ndarray`, `contributions(X) -> DataFrame` (вклад каждого признака в скор строки — для причин).

Параметры по умолчанию. **Гиперпараметры не тюнить** — таково решение команды, ТЗ говорит, что признаки дают больше.

- `logreg`: `StandardScaler` + `LogisticRegression(C=1.0, max_iter=2000)`, NaN → медиана train плюс флаг `_isna`. Вклад = `coef · x_scaled`.
- `lgbm`: `LGBMClassifier(n_estimators=2000, learning_rate=0.05, num_leaves=31, min_child_samples=100, subsample=0.8, subsample_freq=1, colsample_bytree=0.8, random_state=42, verbose=-1)`, ранняя остановка по valid (average_precision, 100 раундов). Категории — нативно (`category` dtype). Вклад — `predict(..., pred_contrib=True)`, отдельного SHAP не нужно.
- `iforest`: `IsolationForest(n_estimators=300, random_state=42)`, скор = `-score_samples`, приводится к [0, 1] по рангу на train. Не является вероятностью — это оговаривается в отчёте.

Seed везде 42. Ресэмплинг (SMOTE, undersampling) не используется: он ломает признаки по истории и вероятности. Решение записано в журнале.

## 9. Судья (`src/evaluate.py`)

```
python -m src.evaluate --config configs/b.yaml                  # все признаки конфига
python -m src.evaluate --config configs/b.yaml --add b_int_1h   # вклад одного признака
python -m src.evaluate --config configs/final.yaml --holdout    # только финал, один раз
```

Каждый запуск дописывает строку в `reports/experiments.csv`:
`datetime, author, config, model, n_features, added_feature, pr_auc, savings, savings_vs_top_p_baseline, savings_vs_rule_amt, recall_cnt, recall_amt, precision, flagged_per_day, split`

Режим `--add`: сравнивает конфиг без признака и с ним, пишет прирост `savings` и `pr_auc`. Так и выполняется правило ТЗ «добавлять признаки по одному».

## 10. Базовая модель (линейка)

`configs/baseline.yaml`: блок `base`, модель `lgbm`, политика `top_p`.

`base` — подготовка, не синтез: `amt`, `log_amt`, `category`, `hour`, `dow`, `is_night` (22:00–03:59), `is_online` (категория оканчивается на `_net`), `age`, `gender`, `log_city_pop`.

От этой строки считается вклад каждого блока. Правило `rule_amt` печатается рядом.

## 11. Тест на заглядывание в будущее (обязателен, запускать после каждого нового признака)

`tests/test_no_future_leak.py`, для каждого блока:
1. Взять 3 случайные даты `T` внутри периода.
2. Посчитать `transform` на `df[df.ts <= T]` и на полном `df` (с одним и тем же `state`).
3. Для строк с `ts <= T` значения должны совпасть (`np.allclose`, NaN == NaN).

Признак, который не проходит тест, в модель не попадает. Если так случилось, запиши в `feature_map.csv` («отброшен: утечка»). Это тоже результат.

Для скорости тест можно гонять на подвыборке **по картам** (например, 100 карт целиком), но не случайными строками — иначе порвётся история.

## 12. Обучение и скоринг

```
python train.py --config configs/final.yaml
python score.py --input <in.csv> --output <out.csv> [--artifacts artifacts/final]
```

`train.py` сохраняет в `artifacts/<name>/`: модель, `state` каждого блока, калибратор, параметры политики, `meta.json` (конфиг, список признаков, версии библиотек, seed, даты разбиения) и `history_tail.parquet` — последние 35 дней операций train+valid+holdout (без `is_fraud`), чтобы у знакомых карт в `score.py` была история.

`score.py` (владелец — B):
- ничего не обучает и не ходит в сеть;
- вход той же структуры без `is_fraud`, порядок строк не гарантирован → сортирует сам;
- склеивает `history_tail` + вход, считает признаки **тем же кодом**, что и при обучении, оставляет только строки входа;
- выход: `trans_num, fraud_probability, decision, reason_1, reason_2, reason_3` (причины только при `decision = 1`, иначе пусто);
- 0,55 млн строк: до 10 минут, до 8 ГБ, без GPU;
- новые карты, мерчанты, категории, города — без падений.

## 13. Отчётность, которую ведём по ходу

- `reports/feature_map.csv` — колонки: `feature, owner, scenario, hypothesis, catches, computed_from, window, no_history_behavior, leak_test, delta_savings, delta_pr_auc, in_final, why`. Отвергнутые признаки остаются отдельными строками.
- `reports/decision_log.md` — развилки: что выбрали, из чего исходили, от чего отказались. «Взяли по привычке» — допустимый честный ответ.
- `reports/experiments.csv` — пишет судья автоматически.

## 14. Правила работы для агента

1. Перед реализацией признака перескажи его гипотезу своими словами и спроси, если формула неоднозначна.
2. Один признак → тест на утечку → `evaluate --add` → строка в `feature_map.csv`. Не добавляй пачкой.
3. Не трогай чужие блоки (`profile.py`, `velocity.py`, `context.py`) — только свой из личного задания. Общие файлы (`data.py`, `split.py`, `evaluate.py`, `economics.py`, `models.py`) меняй только если это нужно всем, и явно сообщи об этом.
4. Не удаляй неудачные признаки из кода: оставь их в `FEATURES`, исключай через конфиг.
5. Никаких оценок на случайном перемешивании, никакого `fraudTest.csv`, никакого холдаута без флага.
6. Если результат подозрительно хорош (PR-AUC > 0,95 после одного признака) — сначала ищи утечку, потом радуйся.
7. Числа в отчёты — только из `experiments.csv`, не из памяти.
